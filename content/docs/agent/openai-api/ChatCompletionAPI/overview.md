## Completions含义

`Completions` 可以理解为 **“完成（completion）”**，这里指的是：

> 给模型一个输入，让模型**补全（生成）后续内容**。

这个名字来自早期的大语言模型使用方式。

在早期 OpenAI API 中，核心接口叫`Completions API`，请求类似：

```json
{
  "model": "text-davinci-003",
  "prompt": "写一首关于春天的诗："
}
```

模型看到，然后进行：

```
写一首关于春天的诗：
            ↓
春风吹过柳枝绿，
花开满园香满地……
```

也就是：模型看到提示(prompt)，进行补全(completion)

```
prompt（提示）
        +
        ↓
模型补全(completion)
```

所以叫 **Completions**。

## 多轮对话

在 **Chat Completions API**（`/v1/chat/completions`）中，由于接口本身是无状态的，服务器不会记住你上一轮说了什么。

因此，实现多轮对话的核心逻辑是：**“上下文追溯”——每次请求时，必须将之前所有的对话历史拼接成一个完整的 `messages` 数组发送给 OpenAI。**

### 第一轮对话

```json
{
  "model": "gpt-4o",
  "messages": [
    { "role": "system", "content": "你是一个精通 Java 的技术专家。" },
    { "role": "user", "content": "你好，我想用 Spring Boot 做一个项目。" }
  ]
}
```

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "你好！Spring Boot 是非常出色的选择。请问你需要什么方向的建议？"
    }
  }]
}
```



### 第二轮对话

用户接着问：“推荐几个常用依赖。”

此时**不能只发这句话**，而是要把【System】+【第一轮 User】+【第一轮 Assistant】+【第二轮 User】**全部拼在一起**发过去：

发送请求：

```json
{
  "model": "gpt-4o",
  "messages": [
    { "role": "system", "content": "你是一个精通 Java 的技术专家。" },
    { "role": "user", "content": "你好，我想用 Spring Boot 做一个项目。" },
    { "role": "assistant", "content": "你好！Spring Boot 是非常出色的选择。请问你需要什么方向的建议？" },
    { "role": "user", "content": "推荐几个常用依赖。" }
  ]
}
```

### 上下文窗口

请求不能无限增长，当接近上下文极限时，通用的做法有：

- 滑动窗口：只保留最近几轮。
- 历史摘要（最常用）：旧对话压缩成摘要。

```json
用户：我负责一个法院案件管理系统
用户：技术栈是Spring Boot
用户：数据库MySQL
用户：正在设计文件管理
...
```

```
摘要：
用户正在开发法院案件管理系统，
后端使用Spring Boot + MySQL，
关注文件管理和OSS设计。
```

```
messages:[
 {
   "role":"system",
   "content":"用户背景摘要：xxx"
 },
]
```

## 温度

在 Chat Completions API 中，**温度（`temperature`）** 是用来控制大语言模型输出**随机性**与**创造力**的采样参数。

简单来说，它决定了模型在预测下一个词时，是倾向于选择“概率最高、最稳妥”的答案，还是愿意尝试“概率稍低、更有创意”的选项。

在生成文本时，模型会给候选词算出一个概率分布：

- **低温度（例如 0 ~ 0.3）：** 拉大词与词之间的概率差距。概率最高词的优势会被大幅放大，模型几乎总是选择那个最确定、最符合逻辑的词。输出结果**稳定、严谨、可重复**。
- **高温度（例如 0.8 ~ 1.5）：** 缩小词与词之间的概率差距。那些概率较低的词也有更大的机会被选到，输出结果会更具**多样性、创造力和随机性**，但也更容易出现逻辑不连贯或胡说八道（幻觉）的风险。

大多数 API（如 OpenAI、DeepSeek 等）的 `temperature` 取值范围通常在 **`0` 到 `2`** 之间（默认值通常为 `1`）：

| **温度值**    | **输出特征**                       | **适用场景**                                     |
| ------------- | ---------------------------------- | ------------------------------------------------ |
| **0.0 - 0.2** | 极度确定，回答高度一致，逻辑严谨   | 代码生成、数据提取/JSON解析、数学计算、精确翻译  |
| **0.5 - 0.7** | 兼顾准确度与回答的丰富度（平衡点） | 通用问答、日常对话、总结报告、技术文档撰写       |
| **0.8 - 1.2** | 发散思维，富于变化，充满灵感       | 文案创作、头脑风暴、角色扮演（RP）、故事续写     |
| **> 1.5**     | 极度随机，逻辑开始变差             | 仅用于极度需要随机性的文学实验（不建议日常使用） |



::: warning

**与 `top_p`（核采样）的关系：** `temperature` 和 `top_p` 都是控制输出随机性的工具。官方通常建议**只修改其中一个**，不要同时调整两者，以免造成采样行为难以预测。

**推理/思考模型（如 DeepSeek-R1 / O1）：** 对于强调逻辑推理的大模型，官方通常会指定一个特定的推荐温度范围（例如 DeepSeek-R1 建议设置为 `0.5 ~ 0.7`），过高会导致逻辑断层，过低可能导致重复循环。

:::
