title: 缓存控制
---

## 为什么需要Cache-Control？

当 HTTP 响应头中完全没有 `Cache-Control`（也没有 Expires）时，浏览器并不会简单地“不缓存”或“强制缓存”，而是会触发 HTTP 规范中定义的一种机制——**启发式缓存（Heuristic Caching）**。

<Callout type="info" title="启发式缓存">
  浏览器会根据响应头中的其他信息（主要是
  Last-Modified），通过一种隐式算法来猜测并自动计算该资源的缓存有效期（即隐式的
  max-age）。
</Callout>

这样导致的后果：

你修改了服务器上的文件，但因为浏览器“自作聪明”把它强缓存了，用户看到的依然是旧页面，直到缓存到期。

## 协商缓存

在 NGINX 中配置 `Cache-Control: no-cache`，对 HTTP 缓存行为会产生明确且关键的影响。很多人常误以为它代表“完全不缓存”，但实际上它的核心含义是“必须协商（强制验证）”。

配置 `Cache-Control: no-cache` 后，浏览器和中间代理服务器（如 CDN）在收到响应时的行为会发生如下转变：

- 允许保存：客户端/代理可以把响应文件保存在本地磁盘或内存中。

- 强制验证：下次再请求该资源时，客户端绝不能直接使用本地缓存，而是必须发送请求到 NGINX 进行协商验证。

- 协商缓存需要配合 `ETag / Last-Modified`：

  - 如果资源没有变动，NGINX 会直接返回 304 Not Modified（不含 Body），客户端直接读取本地缓存。

  - 如果资源已更新，NGINX 会返回 200 OK 以及全新的文件内容。

##  Last-Modified
Last-Modified 就是服务器在响应时附带的一个时间戳，用来告诉浏览器：“这个文件上一次被修改的时间是：XXXX年X月X日 X时X分X秒。”它是 HTTP 中专门用来配合协商缓存使用的响应头



它的工作流程：

<Steps>

<Step>

### 浏览器第一次请求服务器

当你第一次访问某个网页（比如 logo.png）时，服务器会在响应头里带上：

```http
Last-Modified: Wed, 05 Aug 2026 08:58:45 GMT
```

浏览器拿到这个文件后，会把文件和这个时间戳一起存在本地。

<Callout title="注意" type="warn">

HTTP 协议规定 `Last-Modified` 必须用 GMT(UTC)时区表示。北京时间为**UTC+8**

</Callout>



</Step>

<Step>

### 浏览器第二次请求服务器

当你下一次再需要这个 logo.png 时，浏览器会把之前存的时间戳改个名字：`If-Modified-Since`，放在请求头里发给服务器：

```http
If-Modified-Since: Wed, 05 Aug 2026 08:58:45 GMT
```
相当于浏览器在问服务器：“我本地有份 8月5号 的文件，这时间之后你修改过它吗？”

- 如果没变：服务器返回 304 Not Modified（不带文件内容），告诉浏览器“你本地的还能用，直接用吧！”。

- 如果变了：服务器返回 200 OK，并把最新的文件和新的 `Last-Modified` 时间重新发给浏览器。

</Step>

</Steps>
